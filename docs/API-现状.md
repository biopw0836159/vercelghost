## 一、连线方式（不走代理一定失败）

后端有 ipGuard：**未授权来源不会回错误，而是 302 转去 booking.com**。
本机直连 8 个端点，8 个全部被转走 —— 看起来像「后端挂了」，其实是被挡。

所以任何环境（本机、Railway）都必须带 `PROXY_*` 走授权代理，
或者把该环境的出口 IP 加进后端白名单。Railway 出口 IP 不固定，实务上仍要走代理。

## 二之二、B / C 引擎（本站现在的主力）

### C 引擎 `POST /api/query-bet-orders` —— 注单明细

```json
{ "platforms": ["OL"], "dateStart": "2026-08-12", "dateEnd": "2026-08-12",
  "username": "hmhm777", "limit": 5000, "cursor": null }
```

- **`platforms` 必填**：省略、空阵列、`['ALL']` 都拿不到东西（前两者回 400，`ALL` 回 0 笔）。
  本站不写死清单，从 `lottery-stats` 当期实际有资料的平台推导（平台会增减，TD 就是 2026-08 才加的）。
- **每页上限 5000 笔，靠 `nextCursor` 翻页**（`hasMore` 判断有无下一页）。实测翻 6 页 3 万笔零重复。
  （文件写 `limit` 上限 50000，实测无效，仍是每页 5000。）
- **有 `lotteries` 与 `cycleValue` 过滤**（2026-08-15 从官方文件查到，先前盲测漏了）：

  | 参数 | 型别 | 说明 |
  |---|---|---|
  | `lotteries` | `string[]` | 彩种过滤 |
  | `cycleValue` | `string` | 期号精确匹配 |
  | `stateFilter` | `string` | `SETTLED`/`WIN`/`NOPRIZE`/`PROCESS`/`CANCEL` |

  **`lotteries` 吃的是「彩种统计那套名称」**（带编号的 `排列五(15)`），
  不是注单里显示的名称（`排列三五`）—— 传错不会报错、只会安静回 0 笔。

  用后端过滤 vs 拉全量回来自己筛，差距极大（HS 平台 8/12 查「排列五(15)」）：

  | 做法 | 耗时 | 结果 |
  |---|---|---|
  | 后端 `lotteries` 过滤 | **1.3 秒**（翻 1 页） | 852 笔 / 129,449.094 |
  | 拉全量本地精确比对 | 497 秒（翻 125 页、62 万笔） | 852 笔 / 129,449.094 |

  两者数字完全相同，所以一律用后端过滤。
- 栏位比旧端点多 9 个，其中三个关键：
  `real_earn`（后端算好的真实盈亏）、`bet_content`（投注内容号码）、`open_code`（开奖号）。
- **判中奖要看 `status_str`，不能用 `win_count`** —— 实测 772 笔的 `win_count` 全是 0，
  而 `status_str` 分布 `NOPRIZE 609 / WIN 160 / CANCEL 3`，与旧端点 `state` 完全一致。
- 源头把 **CANCEL 撤单也算进投注额**（8/12 hmhm777 有 3 笔、330.00）。本站照源头不动，另外标出笔数金额。

### 本站怎么保证「查多久就拉多久、数字不打折」

1. **边拉边聚合**（`streamBetOrders`）：每页交出来立刻算完就丢原始行，
   内存只吃当下那一页（约 2.5MB），所以翻几百页也不会爆。**不设资料量上限。**
2. **单页失败重试 4 次**，退避 1/2/4/8 秒。实测线上翻到第 101 页时上游会抽风，
   不重试的话就少 8% 资料（787 笔 vs 完整的 852 笔）。
3. **不完整的结果不进快取** —— 否则重跑只会一直拿到同一份残缺资料。
4. **串流回应绕过闸道超时**：Railway 闸道 300 秒没资料就切断，非串流会 502 `upstream error`。
   加 `?stream=1` 改回 NDJSON，每翻一页送一则 `{type:'progress'}`，
   连线持续有资料就不会被切。改用后端 `lotteries` 过滤后一般查询都在数秒内，
   这条主要留给「不指定彩种、要拉整个平台」这类真正的大查询。

> 上面第 4 点的由来：改用后端过滤之前，查彩种得拉全量再本地筛，
> 线上实测 497 秒、翻满 125 页、源头 621,324 笔筛出 852 笔。
> 现在同一查询 1.3 秒。串流机制保留，因为大范围查询仍会超过 300 秒。

### B 引擎 `POST /api/v1/profit-loss` —— 会员盈亏

```json
{ "platform": "OL", "loginId": "hmhm777", "kind": "total",
  "periods": ["today", "month", "lifetime"] }
```

`personal` / `team` 各回 10 栏，**抓鬼五条规则要的全在这里**：

```
bet(销量)  prize(奖金)  returnPoint(返点)  activity(工资)  profit(盈亏，会员视角)
recharge(充值)  withdrawal(提款)  bonus(红利)  depositProfit  proportionalBonus
```

另附 `allAscendants` 代理树（实测 `MERCHANT_REPORT > ol2022 > ybnihao777 > fc999888 > hmhm888`）。

两个硬限制：

1. **只能逐个会员查** —— `loginIds` 阵列、不带 `loginId` 都回 400。实测约 1 秒/人。
   `/api/member-enrich` **不设人数上限**（这是筛选工具，不能因为慢就少查人），
   靠并发 10 把时间压下来。
2. **只有 `today` / `month` / `lifetime` 三个窗口，不吃任意日期区间。**
   查历史日期的注单时，这里补回来的是「今天/本月」的数字，**对应不到那一天**，
   介面上必须显眼标示，不能让人误以为是查询日的数据。

## 四、`member-bets`（注单明细）—— 能用，但不能拿来做全量汇总

回传 `{ records: [...], total }`，单笔栏位：

```
platform, username, user_ip, lottery, play_type, play_name,
cycle_value, position, bet_content_full, bet_amount, win_amount,
state, state_code, bet_time
```

`username` / `cycle_value` / `lottery` 三者至少要传一个，不能只给日期。

**实测把 8/12 全天 77 个彩种拉完的代价：**

| 指标 | 数值 |
|---|---|
| 总耗时 | 109.5 秒（并发 6） |
| 总传输量 | **1715 MB** |
| 单一彩种最大回应体 | **264.9 MB**（台湾PK10，才 4315 笔） |
| 总笔数 | 257,528 |
| 不重复会员 | 4,273 |
| **撞上 10000 笔上限被截断的彩种** | **18 个** |

两个致命点：

1. **10000 笔是硬上限**，`total` 也跟着回 10000（不是真实总数）。`page` / `page_size` 无效，
   只有 `limit` 有效（且只能往下砍）。被截断 = 汇总数字必错。
2. 单次回应可达 264MB，Railway 容器直接吃不消。

> **处置**：`member-bets` 只用于**定向深查**（指定会员、指定彩种、短时窗），
> 不做全量汇总。全量汇总必须由后端出汇总端点。

## 四之二、三个口径陷阱（2026-08-14 实测，全部会导致数字错误）

### 0. `bet_time` 标 `Z` 但存的是当地时间（这条错了会连带切错所有时间）

注单明细的 `bet_time` 长得像 UTC（`2026-08-12T10:01:00.000Z`），但实测它存的是**当地时间**。

用开奖时段固定的彩种当标尺（2026-08-14 实测 8/12 资料）：

| 彩种 | 公认时段 | 字面值 | 当成 UTC 换算 +8 |
|---|---|---|---|
| 经典重庆时时彩 | 每天 10:00 开盘 ~ 次日 02:00 收盘 | **10:01:00 ~ 次日 01:56:00** ✅ | 18:01 ~ 09:56 ❌ |
| 福彩3D | 20:30 开奖 | 样本 175/200 落在 **21 时**（投次日期）✅ | 凌晨 5 点投注 ❌ |

> **结论：直接采用字面值，不做时区位移。**
> `SHIFT_TZ_OFFSET_HOURS` 预设 0，留着是为了万一后端哪天改成真 UTC。

### 1. 日期边界在当地时间 03:00，不是 00:00

用注单量大的会员（`hmhm777`）连查五天，夹逼相邻两天的最晚/最早注单：

| 交界 | 边界落在（字面值） | 间隔 |
|---|---|---|
| 8/11 → 8/12 | 02:53:47 ~ 02:57:40 | 3.9 分钟 |
| 8/12 → 8/13 | 02:52:12 ~ 02:57:44 | 5.5 分钟 |

后端的 `dateStart=D` 实际是「D 当地时间 03:00 → D+1 03:00」。

03:00 这个切点也合理：重庆时时彩 02:00 收盘，凌晨三点是全站最低谷。

> **本站一律照源头口径呈现，不替使用者凑自然日。**
> 前端会明写「查 D 拿到的是 D 03:00 ～ D+1 03:00」，
> B 引擎的结果另外标出这批资料「源头实际涵盖」的起讫时刻，
> 班别分布也按「日期 × 班别」分开列 —— 一次查询本来就横跨两个日期，如实呈现。
>
> 如果要按自然日或按班别对帐，请自行把查询区间往前多带一天，
> 但要知道那样拿到的会是两个业务日的资料，不是后端认定的「一天」。

> **2026-08-14 结论更正**：本节原本写「两个数据源对不上 8%～72%」，**那个结论是错的**。
> 改用 C 引擎拉全量 + 本地字串完全相等比对之后，两边严丝合缝：
> HS 平台 8/12 查「排列三五」得到 **852 笔 / 投注 129,449.09**，
> 与 A 引擎 `lottery-stats` 的「排列五(15)」**852 笔 / 129,449.09 完全一致**。
> 先前的差异全部来自旧端点的串号与 1 万笔截断，**数字本身一直是对的**。
> 下面几小节保留，是为了记住这些坑长什么样。

### 2. `lottery` 参数会串到别的彩种

后端把带编号的彩种名映射到别的彩种，实测：

| 查询 | 实际回来 |
|---|---|
| `排列五(15)` | **排列三五** |
| `QQ分分彩(218)` | QQ分分彩 |
| `谷歌分分彩(251)` | 谷歌分分彩 |
| `波场15秒彩(438)` | 0 笔 |
| `排列`、`谷歌`（部分字串） | 0 笔（所以不是模糊比对） |

挑 14 个彩种交叉核对，**没有一个的名称能对上**，投注额差 12%～72%。

> B 引擎侦测到查询名与实际回传名不符时会跳红字警告。
> **要准确的数字请查会员帐号，不要查彩种。**

### 3. 彩种命名两套：简繁混用 + 编号变体

- **简繁**：`lottery-stats` 写 `经`（U+7ECF），注单明细写 `經`（U+7D93），同一个「经典重庆时时彩」
- **编号变体**：`lottery-stats` 的 133 个基础名里有 **48 组**同名不同编号，
  例如「奇趣腾讯分分彩」214.7 万笔 与「奇趣腾讯分分彩(190)」230.2 万笔是两个独立条目

所以 A 引擎（彩种统计）与 B 引擎（注单明细）的彩种维度**无法可靠对应**。

### 4. 多日查 ≠ 逐日查加总

一次查 8/06～8/12 与逐日查 7 次再加总，结果不同：

| | 一次查 7 天 | 逐日加总 | 差异 |
|---|---|---|---|
| 投注 | 1,882,244,612.36 | 1,862,101,449.01 | 1.082% |
| 笔数 | 57,646,490 | 56,865,290 | 1.374% |
| 平台×彩种组合数 | 734 | 730 | — |

（「人数」差 51% 是预期的：一次查会去重，逐日加总会把同一个人重复计。）

> 这代表**不能用逐日拆分来重建多日数字**。也因此逐日并行加速的方案被否决 ——
> 实测并行 7 天反而要 48.5 秒，比一次查的 7.9 秒更慢。

## 五之二、B 引擎五条规则（2026-08-14 已恢复）

> 改吃 `POST /api/v1/profit-loss` 之后这五条已经恢复，做在 `/api/member-enrich`：

> 盈亏=`profit`（会员视角，正 = 会员赢）、充销比=`bet / recharge`。
>
> ⚠ 窗口只有 today/month/lifetime，查历史日期时这些数字对应不到那一天。

以下为规则原始定义（保留备查）：

B 引擎已改成「定向深查」，原本这五条建在 `member-income` 上的规则先从介面移除。
规则定义记录在这里，后端修好后照这个恢复（栏位来自 member-income：
总投注 `totalSales`、总充值 `deposit`、总返点 `treatment`、总盈亏 `profit`，
充销比 `ratio = totalSales / deposit`，`deposit` 为 0 时 ratio 记 0）。
规则之间是「或」关系，命中任一条就列出，并在「原因」栏标记。

| # | 名称 | 条件 | 原预设值 |
|---|---|---|---|
| ① | 充销比高 + 销量区间 | `deposit > 0` 且 `ratio ≥ ratioHigh` 且 `salesMin ≤ totalSales ≤ salesMax` | ratioHigh 50、销量 30000～99999999 |
| ② | 充销比低 + 充值区间 | `deposit > 0` 且 `ratio ≤ ratioLow` 且 `depositMin ≤ deposit ≤ depositMax` | ratioLow 2、充值 1000～2000 |
| ③ | 高返点 | `treatment ≥ treatmentMin` | 50000 |
| ④ | 大额盈利 | `profit ≥ profitMin` | 100000 |
| ⑤ | 无充值销量高 | `deposit === 0` 且 `totalSales > 0` 且 `totalSales ≥ salesMin` | 5000 |

其中 ①②⑤ 需要充值数据，所以就算 `member-income` 修好，
若它不含充值栏位，这三条仍然要靠 `tx-records`（见第六节第 2 点）。
